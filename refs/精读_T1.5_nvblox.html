1 背景：CPU vs GPU mapping 的功能鸿沟

机器人 path-planning 既要 dense 几何信息（占用、距离），又要快到能 onboard 跑（embedded GPU/CPU）。但现有方案要么 CPU 太慢（voxblox / FIESTA），要么 GPU 又缺关键功能（KinectFusion / NeRF）。nvblox 来填这个空。

1.1 三类竞品的局限

  1. CPU dense mapping（voxblox / FIESTA / Voxfield）—— 有 ESDF 但慢，分辨率上不去；
  2. GPU surface reconstruction（KinectFusion / ElasticFusion）—— 快但只有 surface mesh，无 free space / ESDF，path-planning 没法用；
  3. NeRF（iMAP / NICE-SLAM）—— 需要 heavy keyframing，不够 reactive。
"Previous works leave a gap between CPU-based systems for robotic mapping which, due to computation constraints, limit map resolution or scale, and GPU-based reconstruction systems which omit features that are critical to robotic path planning, such as computation of the Euclidean Signed Distance Field (ESDF)." —— Abstract

1.2 为什么 ESDF 必须 GPU 化

collision query 在 sampling-based / optimization-based planner 里占很大比例。把 query 放 GPU 上能：(1) 利用并行（同时查上千 sample）；(2) 与 GPU-based planner（CuRobo, Riemannian Motion Policies）共享 memory，避免 CPU↔GPU 拷贝；(3) 支持 finer resolution，提高 planning precision。

🎯 一句话定位
nvblox = voxblox 的 GPU 重写 + 一个新的 parallel incremental ESDF 算法。所有 layer（TSDF, ESDF, Color, Mesh, Occupancy）都常驻 GPU memory，包括 query。

2 论文的贡献

① GPU-accelerated SDF library

TSDF 加速 177×，ESDF 加速 31×（vs voxblox），完整保留 voxblox 的可 plan 能力。

② 新 incremental ESDF 算法

基于 Parallel Banding Algorithm (PBA)。把 ESDF 计算分为 Marking → Clearing → Sweeping → Neighbor Update 四阶段，全部并行；不用 quasi-Euclidean 近似（不像 voxblox），保留 full Euclidean accuracy。

③ Embedded GPU 兼容

Jetson Xavier AGX 也能跑实时——ESDF 16× 加速。这是 onboard robot 必备。

④ 开源 + 多平台 ROS

ROS1, ROS2, Isaac ROS 三套包装。已被 CuRobo / Riemannian Motion Policies 使用。

🏆 核心数字成果（来自 Table I, II, III）
  • TSDF：Replica @ Desktop 0.4 ms（vs voxblox -，与 voxblox TSDF+Color 86.7 ms 比 ×174 加速）；
  • ESDF：Replica @ Desktop 1.9 ms（vs voxblox 163.2 ms，×63 加速）；Average 平均 ×31 加速 vs voxblox，×7 vs Fiesta；
  • ESDF accuracy：median error 0.06 m（与 voxblox 0.07 / Fiesta 0.06 相当——速度提升不以精度为代价）；
  • Mesh：Replica @ Desktop 1.6 ms (×3 加速)；Redwood @ Desktop 0.6 ms (×13 加速)；
  • Query rate：Desktop 6.2 G queries/s (correlated)；Jetson uncorrelated 3 ns/point；
  • LiDAR 64-beam @ 25 m / 10 cm：Laptop < 7 ms; Jetson < 20 ms（≥ 2× real-time）。

3 LayerCake 架构总览

nvblox 的世界模型叫 LayerCake：多个 co-located、aligned 的 3D voxel grids（layers）。每个 layer 存不同 quantity：TSDF, ESDF, Color, Occupancy, Mesh。

┌──────────────────────────────────────────────────────────────────────┐ │ INPUT │ │ Depth Image D : Ω → ℝ (RGB-D camera 或 LiDAR) │ │ Color Image C : Ω → ℝ^3 │ │ Sensor Pose T_LC_i ∈ SE(3) │ └──────────────────────────────────────────────────────────────────────┘ │ ▼ ┌────────────────────┴────────────────────────┐ ▼ ▼ TSDF Integrator Color Integrator per-voxel update functor per-voxel update d_p = d - d_v (projective dist) weighted RGB average weight w = f_w(d_p) │ weighted-average distance + truncate │ │ │ ▼ │ TSDF Layer ────────────┐ │ (8×8×8 VoxelBlock, hash table via stdgpu) │ │ │ │ ▼ ▼ ▼ Mesh Integrator ESDF Integrator Color Layer Parallel Marching Cubes Marking → Clearing │ → Sweep within block ▼ → Update Neighbor Blocks Mesh Layer (loop until converged) │ ▼ ESDF Layer (sites + children, parent direction) │ ▼ Query: collection of 3D points → distances + ∇d (on GPU, no CPU↔GPU copy) Desktop 6.2 G queries/s, Jetson 0.5–0.8 G queries/s

3.1 三件存储设计

  • 稀疏 hashing：第 1 级 GPU hash table (via stdgpu) 映射 3D grid index → VoxelBlock pointer；第 2 级 VoxelBlock 是 8×8×8 dense voxels，contiguous in memory（GPU coalesced loads）；
  • 可扩展 layer：用户定义 voxel content struct，编译期生成 hash grid + CPU/GPU interface；
  • Layer alignment：所有 layer 共享同一 voxel grid 坐标系，便于跨 layer 查询。
💡 LayerCake = 关键 API
LayerCake 不是单一 voxel struct，是一组 co-located 但不同语义 的 voxel grids。这给了 EvidLife-Map 直接 plug-in 的空间——加一个 EvidentialLayer，存 Dirichlet $\alpha^c$ + decay timestamp，就能与 TSDF/ESDF 共享坐标系。

4 关键模块拆解

4.1 Frame Integration（§IV.B）

核心数学公式（每个 voxel 在视野内的投影）：

$$d = D[\pi_{\mathrm{sensor}}(T_{CL} p_L)] \tag{1}$$

其中 $T_{CL}$ 是 camera pose w.r.t. Layer 坐标系，$p_L$ 是 voxel 中心位置。Sensor projection 分两种：

$$\pi_{\mathrm{camera}}(p_C) = \frac{1}{p_{C,z}} \begin{bmatrix}f_u & 0 & c_u\\ 0 & f_v & c_v\end{bmatrix} \begin{bmatrix}p_{C,x}\\ p_{C,y}\\ 1\end{bmatrix} \tag{2}$$
$$\pi_{\mathrm{lidar}}(p_C) = \begin{bmatrix}(\tan^{-1}(p_{C,y}/p_{C,x}) - \theta_{\mathrm{start}}) \cdot \alpha_\theta \\ (\cos^{-1}(p_{C,z}/r) - \phi_{\mathrm{start}}) \cdot \beta_\phi \end{bmatrix} \tag{3}$$

$\alpha_\theta, \beta_\phi$ 是 pixels-per-radian（FoV/beams）。LiDAR 用 linear interpolation（同时处理前-背景边界）。

TSDF update functor

对每个 voxel：

  • 计算 voxel-to-sensor 投影距离 $d_p = d - d_v$；
  • truncate 到 $[-\epsilon, +\epsilon]$；
  • $w = f_w(d_p)$（恒定 / sensor error model）；
  • weighted average distance：$d_{\mathrm{tsdf}} \leftarrow (d_{\mathrm{tsdf}} \cdot w_{\mathrm{old}} + d_p \cdot w) / (w_{\mathrm{old}} + w)$；
  • weight sum：$w \leftarrow w_{\mathrm{old}} + w$ 上限到 $w_{\max}$。

Occupancy update functor

log-odds Bayesian fusion (Thrun)：

  • $d_p > 0$（voxel before surface）→ 加常数负值（free 概率高）；
  • $d_p < 0$（voxel behind surface）→ 加常数正值（occupied 概率高）。

4.2 ESDF Computation（§IV.C，论文核心创新）

整个 ESDF 算法是 incremental + parallel。算法流程（Fig. 3 + Fig. 5）：

[step 1] Allocate Blocks 输入: TSDF layer + 更新的 VoxelBlock 列表 分配 ESDF 端新出现的 VoxelBlocks [step 2] Mark Sites site = surface boundary voxel - TSDF case: TSDF distance 在 ±ε 内 → site - Occupancy case: 邻接 free → site 处理两种特殊情形: (A) newly occupied/observed: 直接采用 TSDF 距离，加入 Indices to Update (B) newly freed: 距离 set invalid; 若它本是 site 则其所有 children 都要 invalidate (加入 Indices to Clear) [step 3] Clear Invalid 找到 parent 不再是 site 的 voxels → distance set 到 max 在 max ESDF distance 范围内并行检查，加入 Cleared Indices [step 4] Lower ESDF (循环至收敛) [4a] Sweep within block (基于 PBA 思想) 在每个 VoxelBlock 内独立做 X+, X-, Y+, Y-, Z+, Z- 6 次 sweep 每次 sweep: 若邻居方向有更短路径到 site，就更新该 voxel 所有 affected blocks 在同一 kernel call 内并行 [4b] Update Neighbor Blocks 跨 block 边界传播 若邻居 block 边缘有更短距离，propagate 进来 若边界发生通信，affected block 标记 → 回到 [4a] loop until no more blocks updated
💡 为什么不用 voxblox 的 quasi-Euclidean？
voxblox 用 quasi-Euclidean 近似换速度，引入系统误差。nvblox 用 full Euclidean（PBA-style sweep），不仅没变慢反而更快，因为 GPU parallelism 让 sweep cost 摊销了。这是论文最 clever 的工程贡献。

4.3 Mesh Integrator

对 TSDF 已更新的 block 周期性运行 parallelized Marching Cubes。论文未给详细公式，是标准实现。Replica @ Desktop 1.6 ms。

4.4 Sites 与 Children 数据结构（Fig. 4）

每个 ESDF voxel 三种状态：unknown / free（正距离）/ occupied（负距离）。site = surface 边界 voxel。每个 child voxel 存它的 parent direction——指向最近 site 的方向。这个结构让 incremental 更新只需重新计算 invalidate 的子树，而不是全图。

7 Ablation / Scaling Studies

7.1 Resolution sweep

论文 Fig. 6 显示 nvblox 和 voxblox 在 voxel size 5–20 cm 范围内的 TSDF/ESDF time。nvblox 曲线几乎平直（GPU parallelism 摊销了 voxel 数量），voxblox 随 resolution 变细呈指数恶化。

7.2 Query 模式（spatial correlation）

Table III 的 cor. vs uncor.：

  • Correlated（同 VoxelBlock）：GPU coalesced memory access → 2× faster；
  • Uncorrelated：random hash misses，速度降一半但仍可用。

这对 EvidLife-Map 重要：vacuity-based traversability 查询往往是 spatial-correlated（围绕机器人当前位置），可获最佳吞吐。

7.3 Application examples（Fig. 7, 8）

  • 飞行机器人 LiDAR mapping（大尺度户外）；
  • 机械臂高速 adaptive planning（CuRobo 集成）；
  • 地面机器人 office mapping with people segmentation（PeopleSemSegnet [TAO] 分动静）。

最后一个 动静分离 示例最相关：用单独的 OccupancyLayer 存 dynamic 人体（在静态 TSDF 上 overlay），动态部分 decay over time。这就是 EvidLife-Map decay 思想的雏形——但 nvblox 用的是 occupancy log-odds，不是 evidential。

8 局限性

✅ 优势
  • 177× TSDF / 31× ESDF 加速 + 精度不下降；
  • Embedded GPU (Jetson) 可跑；
  • 多 layer 架构可扩展；
  • GPU-resident query 与 GPU planner 直接对接；
  • 已被 CuRobo、Riemannian Motion Policies 等真实系统使用。
⚠️ 局限
  • 仅支持 RGB-D / LiDAR，未直接处理纯 stereo 或 monocular；
  • 无语义（论文用 PeopleSemSegnet 外部分 dynamic，但 layer-level 不存语义概率）；
  • 无 evidential / uncertainty：occupancy 是 log-odds，TSDF 是 weighted average，没显式 epistemic uncertainty；
  • 无 loop closure：依赖外部 SLAM（论文用 FAST-LIO）提供 pose；
  • 动态对象 decay 是 application-level 而非 framework-level；
  • 不公开训练数据，但 nvblox 不是 learning-based，所以无影响。

9 与 EvidLife-Map 的关系（API plug-in 视角）

nvblox 是 EvidLife-Map 的 SDF 体素 backbone——R2 reviewer 明言"不引就 desk-reject"。我们必须把 evidential 层挂到 nvblox 的 LayerCake 上，而不是从头实现 SDF。

9.2 plug-in 步骤

  1. 定义 EvidentialVoxel struct：包含 $\alpha^1 \dots \alpha^C$ (C=20 for SemanticKITTI)、decay_timestamp、last_obs_pose_idx。预估大小 = 4·20 + 4 + 2 = 86 bytes/voxel。VoxelBlock = 8×8×8 = 512 voxels = 44 KB/block。注意：原 TsdfVoxel = 8 bytes/voxel，EvidentialVoxel 增至 86 bytes —— hash table size 不变但 per-block memory 增长 ~11×；
  2. 编译期自动生成：nvblox 的 layer mechanism 会自动为 EvidentialVoxel 生成 hash grid + CPU/GPU interface（按论文 §IV.A）；
  3. 实现 EvidentialIntegrator：参考 TsdfIntegrator 的 per-voxel update functor 模式，把 ConvBKI 的 depthwise conv update 改写成 nvblox 的 voxel-parallel kernel；
  4. 共享坐标系：与 TsdfLayer / EsdfLayer co-located，所以一次 ESDF query 同时返回 clearance + vacuity（cross-layer query）。

9.3 体素哈希结构能否扩展到 evidential + decay？

Yes——这是 nvblox LayerCake 设计的核心优势。论文 §IV.A 明确写："The map is designed to be extended with new layers. To create a new Layer, a user needs to specify the contents of a single voxel."。所以我们只需提供 EvidentialVoxel 的 C++ struct，nvblox 自动生成所有 hashing / GPU kernel template。不需要 fork nvblox。

9.4 GPU 内存占用模型

关键限制：nvblox 用 dense 8×8×8 VoxelBlock，sparse hashing 只在 block 级。所以单个 block 的 memory 直接乘以 voxel content size：

$$\mathrm{mem}(\mathrm{Block}) = 512 \cdot \mathrm{sizeof}(\mathrm{Voxel}),\quad \mathrm{mem}(\mathrm{Map}) = N_{\mathrm{blocks}} \cdot \mathrm{mem}(\mathrm{Block})$$

对 SemanticKITTI 20 类、Replica-scale map（typ. ~5000 blocks）：

  • TsdfLayer 单 layer: 5000 × 4 KB = 20 MB；
  • EvidentialLayer (C=20): 5000 × 44 KB = 220 MB；
  • + ESDF (10 MB) + Color (15 MB) + Mesh (~30 MB) = total ~280 MB；
  • RTX 3090 24 GB → 完全可用；Jetson Xavier AGX 32 GB unified → 也 OK。

但：若 EvidentialLayer 扩到 C=100 类（开放词表场景），mem = 5000 × 204 KB = 1.0 GB。这是必须考虑的 scalability 边界——R2 reviewer 可能会问。

9.5 decay 字段的存储设计

每个 voxel 多存：

  • last_obs_timestamp (uint32)：4 B。decay rule 用 $\alpha^c_{\mathrm{new}} = \lambda^{\Delta t} \cdot \alpha^c_{\mathrm{old}}$，每次 integrate 时根据 $\Delta t = t_{\mathrm{now}} - t_{\mathrm{last}}$ 衰减；
  • last_obs_pose_idx (uint16)：2 B。用于 lifetime tracking + 与 trajectory 关联；
  • option：alpha_dirty_bit (1 B)——标记 voxel 被衰减但未重新观测，便于批量清理；

nvblox 的 incremental ESDF 算法已经有"newly freed voxel → invalidate children"机制（§IV.C），我们的 decay 也可以借此结构——decayed-to-low-α voxel 触发 ESDF re-compute。

9.6 实现注意（写进 R2 response）

⚠️ 5 条 R2 reviewer 关心的点
  1. 共享 hash table：所有 layer 共享 block index 空间，所以 EvidentialVoxel 的 allocate/deallocate 必须与 TsdfLayer 同步——nvblox 的 LayerCake 类已经处理；
  2. integrator 顺序：TsdfIntegrator 必须先跑（决定 block allocation），EvidentialIntegrator 跟随；ESDF 需要 TSDF；
  3. query 性能：cross-layer query 在 GPU 上 zero-copy，6.2 G queries/s on Desktop（Table III）；
  4. resolution 一致性：所有 layer 应同分辨率（默认 5 cm 或 0.2 m），EvidLife-Map 与 ConvBKI baseline 对齐到 0.2 m；
  5. ROS 接口：Isaac ROS nvblox 已包装好 RViz visualization，我们只需添加 vacuity color-coded mesh marker。

10 总结

10.1 一句话总结

nvblox 是 voxblox 的 GPU 重写 + 一个新的并行 incremental ESDF 算法，把 TSDF 加速 177×、ESDF 加速 31×（vs voxblox），精度不下降；通过可扩展的 LayerCake 架构、stdgpu hash table 和 8×8×8 VoxelBlock 设计，所有 layer 常驻 GPU memory；Jetson 也能实时跑。

10.2 对 EvidLife-Map 的核心 takeaway

  1. 不要 fork nvblox——LayerCake 已经提供"用户定义 voxel content struct → 编译期生成 hash grid + GPU kernel template"的机制，我们只需写 EvidentialVoxel struct + EvidentialIntegrator；
  2. EvidentialLayer 与 TSDF / ESDF 共享坐标系——cross-layer query 在 GPU 上 zero-copy；
  3. per-block memory 警觉：C=20 时 EvidentialVoxel 44 KB/block，比 TSDF 大 11×；C=100 时 204 KB/block——必须做 ablation；
  4. incremental decay 蹭 nvblox 的 invalidate-children 机制——voxel decay 到阈值以下可以触发 ESDF re-compute，避免显式清理 loop。

10.3 实现注意（R2 response 直接照用）

  • 基于 github.com/nvidia-isaac/nvblox v0.0.5+（ICRA 2024 版本）；
  • 添加 EvidentialLayer，voxel content = α[C] + ts + pose_idx；
  • integrator 顺序：Tsdf → Color → Evidential → ESDF → Mesh；
  • 分辨率与 ConvBKI baseline 对齐 0.2 m；
  • Jetson Xavier 测试以证 onboard 可行性。
